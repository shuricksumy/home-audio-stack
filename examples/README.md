# A working example

This is the whole house in one compose file — the real setup, with addresses and
passwords replaced. Every room, two transports, one place to press play.

```bash
mkdir -p data/squeezelite-panel data/snapcast-panel data/bluetooth-web-config
sudo chown -R 1000:1000 data          # or your own uid, see PUID below
cp .env.example .env                  # set HOST_IP, PUID and the passwords
docker compose up -d
```

Then open Music Assistant at `http://<host>:8095` and add your players in the
panels:

| | |
| :-- | :-- |
| `http://<host>:8080` | **squeezelite panel** — one player per wired DAC, bit-perfect |
| `http://<host>:8081` | **Snapcast panel** — one player per synced room |
| `http://<host>:8088` | **Bluetooth panel** — pair a speaker, it becomes a room |

You do not edit this file to add a room any more: the three services below are
web panels, and each one creates, starts and supervises as many players as you
have outputs. The players are stored under `data/` and come back on restart.

## What is in it

| Service | Role | Reached over |
| :-- | :-- | :-- |
| `music-assistant-server` | the brain: library, streaming, and the servers the players connect to | host network |
| `squeezelite-panel` | a player per wired USB DAC, bit-perfect, created from a browser | Squeezelite (SlimProto, 3483) |
| `snapcast-panel` | a player per synced room, created from a browser | Snapcast (1704) |
| `bluetooth-web` | every Bluetooth speaker, paired from a browser | Snapcast (1704) |
| `ledfx` | WLED strips reacting to the music | both, feeding LedFx |
| `bubbleupnpserver` | optional: makes it all visible to UPnP/DLNA devices | host network |

## Why two transports

**Squeezelite for wired DACs.** It hands the audio over untouched, so the DAC
follows the track's own rate — 44.1, 96, 192 kHz, 16- or 24-bit — instead of
everything being resampled to one format. That is the whole point of owning a
good DAC.

**Snapcast for Bluetooth and LedFx.** Snapcast's job is keeping rooms on one
clock. Bluetooth is not bit-perfect anyway (A2DP re-encodes), so sync is what
matters there, and LedFx only needs to hear the music.

Both are Music Assistant providers, so every player shows up in the same list.

## Before it works

**The host must be a working PipeWire machine.** Every player here attaches to
the host's audio session rather than running its own daemon. That setup —
installing PipeWire, enabling lingering so it survives logout, and checking the
socket exists — is written out once in
[pipewire-snapclient](https://github.com/shuricksumy/pipewire-snapclient#-host-setup-preparation)
and applies to all of them.

**You no longer need the node names up front.** Each panel lists the host's
outputs in a dropdown when you add a player. If you want to see them yourself,
or you are writing a single-player service by hand:

```bash
pw-cli ls Node | grep -E 'node.name|node.description'
```

**Host networking means one port each.** All three panels default to 8080, and
two of them run on the host's network stack, so the compose file moves the
Snapcast one to `PORT=8081`. Change `PORT`, not a `ports:` mapping, for those.

**Check your uid.** `PUID` must own `/run/user/<uid>/pipewire-0`:

```bash
id -u
```

**Every Squeezelite player needs its own MAC.** It is how the server tells them
apart, and two players sharing one will fight over a single slot. Leave the
field blank in the panel and it generates a unique locally-administered address
for you; if you fill it in yourself, start it with `02:`.

## Three things that will bite you

**One player per output device.** The panels each keep their own list and
cannot see each other's, so nothing stops you pointing the squeezelite panel and
the Snapcast panel at the same DAC — and they will not share it, they will fight
over it. The symptom is distorted or silent audio, or a player that will not
start, with nothing useful in either log. Decide per device which transport owns
it: Squeezelite for the DACs you care about, Snapcast for everything that has to
stay in sync.


**On Ubuntu, keep `security_opt: [apparmor=unconfined]` on `bluetooth-web`.**
Docker's default AppArmor profile grants no D-Bus rules, so the container is
refused before it can talk to `bluetoothd`, and the error it produces is not
obvious. Debian and Alpine hosts do not need it.

**Bluetooth rooms arrive late.** A2DP adds roughly 150–250 ms. Playing alongside
a wired room, set a negative latency offset on the Bluetooth player in the panel
and tune by ear until they line up.
